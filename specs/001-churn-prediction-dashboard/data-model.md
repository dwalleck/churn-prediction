# Data Model: Customer Churn Prediction Dashboard

**Feature**: 001-churn-prediction-dashboard
**Date**: 2025-10-22
**Status**: Phase 1 Design

## Overview

This document defines the data entities, their attributes, relationships, and validation rules for the churn prediction system. The model supports CSV data ingestion, ML-based scoring, and dashboard queries.

## Storage Architecture

- **S3 Buckets**: Raw CSV files, preprocessed features, trained models, historical archives
- **DynamoDB Tables**: Live customer churn scores with GSI for risk-level queries
- **Local Development**: File-based storage in `data/` directory

## Entities

### 1. Customer

**Purpose**: Represents a customer account with attributes used for churn prediction

**Source**: CSV upload (weekly batch)

**Attributes**:

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| account_id | string | Yes | Unique customer identifier | Non-empty, alphanumeric |
| month | date | Yes | Data snapshot month (YYYY-MM) | Valid date format |
| current_month_transactions | integer | Yes | Transaction count this month | >= 0 |
| current_month_revenue | float | Yes | Revenue this month ($) | >= 0 |
| total_tickets | integer | Yes | Support tickets opened | >= 0 |
| escalated_tickets | integer | Yes | Escalated support tickets | >= 0, <= total_tickets |
| late_payments | integer | Yes | Late payment count | >= 0 |
| enabled_channels | integer | Yes | Active service channels | >= 0 |
| self_service_percentage | float | Yes | Self-service usage (%) | 0-100 |
| last_touchbase_date | datetime | Yes | Last interaction timestamp | <= current date |
| average_resolution_time_hours | float | Yes | Avg support resolution time | >= 0 |
| churned | integer | Yes | Churn label (0=active, 1=churned) | 0 or 1 |

**Derived Features** (calculated during preprocessing):

| Field | Type | Description | Calculation |
|-------|------|-------------|-------------|
| tenure_months | integer | Customer age in months | Count of distinct months for account_id |
| transaction_change_pct | float | MoM transaction change | (current - previous) / previous * 100 |
| revenue_change_pct | float | MoM revenue change | (current - previous) / previous * 100 |
| days_since_last_touchbase | integer | Recency of last contact | (current_date - last_touchbase_date).days |
| ticket_escalation_rate | float | % of tickets escalated | escalated_tickets / total_tickets * 100 |
| revenue_per_transaction | float | Average transaction value | current_month_revenue / current_month_transactions |

**State Transitions**: None (immutable historical records)

**Relationships**:
- One Customer record → One ChurnScore (per scoring run)
- One Customer record → One ChurnEvent (if churned=1)

---

### 2. ChurnScore

**Purpose**: Stores calculated churn probability for each customer

**Source**: Generated by ML prediction pipeline (weekly batch)

**Storage**: DynamoDB table `churn-scores`

**Attributes**:

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| account_id | string | Yes | Customer identifier (partition key) | Matches Customer.account_id |
| score_date | date | Yes | Scoring run date (sort key) | Valid date |
| churn_probability | float | Yes | Churn risk score (0-100) | 0-100 |
| risk_level | string | Yes | Risk category | "low", "medium", "high" |
| confidence | float | Yes | Model confidence | 0-1 |
| model_version | string | Yes | Model identifier | Semver format |
| top_risk_factors | list[dict] | Yes | Top 3 contributing features | [{feature, importance}] |
| created_at | datetime | Yes | Record creation timestamp | Auto-generated |

**DynamoDB Schema**:
- **Primary Key**: account_id (partition), score_date (sort)
- **GSI-1**: risk_level (partition), churn_probability (sort) - for "show all high-risk customers" queries
- **TTL**: None (retain all historical scores for trend analysis)

**Validation Rules**:
- `risk_level` mapping: low (0-30), medium (31-69), high (70-100)
- `top_risk_factors` must contain exactly 3 elements
- `churn_probability` rounds to 2 decimal places

**Relationships**:
- One ChurnScore → One Customer (account_id FK)
- Many ChurnScores per Customer (time series, one per weekly scoring run)

---

### 3. ChurnEvent

**Purpose**: Records historical churn occurrences with categorized reasons

**Source**: Extracted from Customer records where churned=1

**Storage**: DynamoDB table `churn-events` or CSV historical archive

**Attributes**:

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| event_id | string | Yes | Unique event identifier | UUID |
| account_id | string | Yes | Customer who churned | Matches Customer.account_id |
| churn_date | date | Yes | Month of churn | Valid date |
| churn_reason_category | string | Yes | Categorized reason | Valid category |
| churn_reason_detail | string | No | Free-text detail | Max 500 chars |
| final_revenue | float | Yes | Last month revenue | >= 0 |
| final_transactions | integer | Yes | Last month transactions | >= 0 |
| tenure_at_churn | integer | Yes | Customer tenure when churned | > 0 |
| created_at | datetime | Yes | Record creation | Auto-generated |

**Churn Reason Categories** (enum):
- `price_cost`: Price/cost concerns
- `product_quality`: Product/service quality issues
- `customer_service`: Poor customer service experience
- `competitor`: Switched to competitor
- `business_closed`: Customer business closed/no longer needs service
- `other`: Uncategorized reasons

**Validation Rules**:
- `churn_reason_category` must be one of valid categories
- If `churn_reason_category = "other"`, `churn_reason_detail` is required

**Relationships**:
- One ChurnEvent → One Customer (account_id FK)
- Many ChurnEvents → One ChurnReasonCategory (aggregation)

---

### 4. ActionableRecommendation

**Purpose**: Suggested retention actions for high-risk customers

**Source**: Generated by recommendation engine based on ChurnScore and risk factors

**Storage**: DynamoDB table `recommendations` or embedded in ChurnScore

**Attributes**:

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| account_id | string | Yes | Customer identifier | Matches Customer.account_id |
| recommendation_id | string | Yes | Unique recommendation ID | UUID |
| action_type | string | Yes | Category of action | Valid action type |
| priority | integer | Yes | Action priority (1-3) | 1, 2, or 3 |
| description | string | Yes | Human-readable action | Max 200 chars |
| rationale | string | Yes | Why this action | Max 300 chars |
| estimated_impact | string | Yes | Expected outcome | "high", "medium", "low" |
| created_at | datetime | Yes | Recommendation date | Auto-generated |

**Action Types** (rule-based on risk factors):
- `immediate_contact`: Reach out within 24-48 hours
- `offer_discount`: Price-based retention offer
- `schedule_training`: Product education/onboarding
- `review_service`: Service quality check-in
- `contract_renewal`: Proactive renewal discussion

**Recommendation Logic** (examples):
- If `days_since_last_touchbase > 60` → `immediate_contact`
- If `revenue_change_pct < -30%` and high score → `offer_discount`
- If `ticket_escalation_rate > 50%` → `review_service`
- If `tenure_months < 3` and high score → `schedule_training`

**Relationships**:
- Many ActionableRecommendations → One ChurnScore
- One ActionableRecommendation → One Customer

---

### 5. ModelMetadata

**Purpose**: Tracks trained ML models and their performance metrics

**Source**: Generated during model training pipeline

**Storage**: S3 (model artifacts) + DynamoDB (metadata)

**Attributes**:

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| model_version | string | Yes | Semantic version (partition key) | Semver format |
| trained_at | datetime | Yes | Training timestamp | Auto-generated |
| training_data_path | string | Yes | S3 path to training data | Valid S3 URI |
| model_artifact_path | string | Yes | S3 path to model file | Valid S3 URI |
| algorithm | string | Yes | ML algorithm used | "xgboost", "random_forest", etc. |
| hyperparameters | dict | Yes | Model configuration | JSON object |
| performance_metrics | dict | Yes | Evaluation metrics | JSON with f2_score, pr_auc, etc. |
| feature_importance | dict | Yes | Feature importance scores | {feature: importance} |
| is_active | boolean | Yes | Currently deployed model | true/false |

**Performance Metrics Structure**:
```json
{
  "f2_score": 0.75,
  "precision": 0.68,
  "recall": 0.82,
  "pr_auc": 0.79,
  "lift_at_10pct": 3.2,
  "threshold": 0.35
}
```

**Validation Rules**:
- Only one model can have `is_active = true` at a time
- `performance_metrics` must include minimum: f2_score, precision, recall, pr_auc

## Data Flow

### CSV Upload → Scoring Pipeline

```
1. CSV uploaded to S3 bucket (s3://churn-data/raw/YYYY-MM-DD.csv)
2. Lambda triggered on S3 upload event
3. Data validation (schema, ranges, duplicates)
4. Feature engineering (derive tenure, changes, recency)
5. Load active model from S3
6. Generate predictions (churn_probability, risk_level)
7. Calculate top risk factors (SHAP values)
8. Generate recommendations (rule-based logic)
9. Write ChurnScore + ActionableRecommendation to DynamoDB
10. Archive processed data to S3 (s3://churn-data/processed/)
```

## Data Validation Rules

### CSV Upload Validation

**Pre-Processing Checks**:
1. File size < 100MB
2. Valid CSV format (UTF-8 encoding)
3. Required columns present
4. No duplicate (account_id, month) pairs
5. Numeric fields parseable
6. Dates in valid format

**Data Quality Checks**:
1. At least 100 customer records
2. At least 5% positive churn examples (class balance)
3. No more than 10% missing values per column
4. Numeric ranges within expected bounds
5. Temporal consistency (months in sequence)

**Error Handling**:
- Invalid CSV → Return detailed error message, do not process
- Missing optional fields → Fill with defaults or null
- Outliers → Log warning, cap at percentile thresholds

### Model Scoring Validation

**Pre-Scoring Checks**:
1. Model artifact exists and is loadable
2. Input features match model schema
3. Feature values within training distribution

**Post-Scoring Checks**:
1. All scores between 0-100
2. Risk level distribution reasonable (not all high/low)
3. At least 3 risk factors per customer

## Indexes and Performance

### DynamoDB Indexes

**Table: churn-scores**
- Primary: (account_id, score_date)
- GSI-1: (risk_level, churn_probability) - for high-risk queries
- Provisioned throughput: On-demand (cost optimization)

**Table: churn-events**
- Primary: (event_id)
- GSI-1: (churn_reason_category, churn_date) - for reason aggregation
- Provisioned throughput: On-demand

**Query Performance Targets**:
- Get customer score: <10ms (single-item lookup)
- Get high-risk customers: <50ms (GSI query, limit 100)
- Aggregate churn reasons: <100ms (GSI query + aggregation)

## Migration and Versioning

**Schema Evolution**:
- Backward compatible changes only (add optional fields)
- Major changes require new DynamoDB table + data migration
- Model version tracking ensures reproducibility

**Data Retention**:
- Customer raw data: 2 years in S3
- Churn scores: All historical scores (enable trend analysis)
- Model artifacts: Last 5 versions
- Logs: 90 days

## Security and Privacy

**Data Classification**: Customer PII (account identifiers)

**Access Control**:
- S3 buckets: Private, IAM role-based access
- DynamoDB: IAM policies, no public access
- Dashboard: Authentication required (AWS Cognito or similar)

**Encryption**:
- S3: Server-side encryption (SSE-S3)
- DynamoDB: Encryption at rest enabled
- In-transit: TLS 1.2+

**Compliance Considerations**:
- No credit card data stored
- Customer identifiers anonymized in logs
- Data deletion on customer request (GDPR compliance)
